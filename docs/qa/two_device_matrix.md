# بروتوكول اختبار الجهازين · Allo Service

> **الهدف:** إثبات دورة الحساب كاملة (تسجيل → وثائق → مراجعة → موافقة → Dashboard → Disponible)
> على **جهازين حقيقيين متزامنين**، لأن اختبارات الوحدة تُثبت منطق الكود ولا تُثبت التزامن.
>
> **المدة:** ~20 دقيقة · **المتطلبات:** هاتفان (أو محاكيان بذاكرة مستقلة) + مشروع Supabase حيّ.

---

## 0. التحضير

| # | الخطوة |
|---|---|
| 0.1 | جهاز **A** = التطبيق بحساب محترف جديد (`pro.a@…`) |
| 0.2 | جهاز **B** = لوحة الأدمن في التطبيق (أو Supabase Dashboard) |
| 0.3 | على الجهازين: فعّل تسجيل اللوغ — `flutter run` أو `adb logcat \| findstr allo` |
| 0.4 | تأكّد من نظافة البداية على A: إعدادات النظام ← التطبيق ← **مسح البيانات** |

**كيف نسجّل النتيجة؟** لكل سيناريو: ✅ / ❌ + صورة الشاشة + آخر 20 سطر لوغ.

## 1. المصفوفة

| # | السيناريو | الخطوات | المتوقّع على A | الدليل في اللوغ / القاعدة |
|---|---|---|---|---|
| **S1** | موافقة والأجهزة مسكّرة | A: سجّل محترف، ارفع الوثيقة، **أغلق التطبيق تمامًا**. B: وافق. A: افتح التطبيق | **Dashboard** مباشرة (بلا `pending`) | `professionals.status = 'approved'` · لوغ: `syncSessionStoresForCurrentUser` بلا انتقال لـ`pending` |
| **S2** | موافقة والـA مفتوح على شاشة الانتظار | A: افتح التطبيق، ابقَ في «في انتظار التحقق». B: وافق (**دون لمس A**) | خلال **≤ 10 ثوانٍ** تتحوّل الشاشة للـ**Dashboard** وحدها | لوغ: استدعاء متكرّر لـ`VerificationSyncService.syncNow` كل 10s |
| **S3** | رفض + سبب + إعادة إرسال | B: ارفض مع سبب. A: افتح | «تم رفض الحساب» + **سبب الرفض** + زرّان: معرض/كاميرا | `professionals.status = 'rejected'` + `rejection_reason` غير فارغ |
| **S4** | إصلاح الوثيقة (المعرض) | A: «إعادة رفع الإثبات» ← **اختيار من المعرض** ← اختر صورة ← أرسل | الشاشة ترجع لـ«في انتظار التحقق» | `professional_resubmit_own_proof` نجح · `status = 'pending'` |
| **S5** | A أوفلاين لحظة الموافقة | A: **وضع الطيران**. B: وافق. A: أطفئ الطيران | «جارٍ التحقق» ثم **Dashboard** — **ولا مرة** `pending` | لوغ: `verificationUnconfirmed` أثناء الفشل، ثم تأكيد |
| **S6** | إعادة تشغيل بعد الموافقة | A: **أغلق التطبيق وافتحه 3 مرات** | Dashboard في كل مرة (بلا وميض `pending`) | `admin_pending_pros_json` لا يحتوي سجلًا مكرّرًا للحساب |
| **S7** | انقطاع ثم عودة | A: Dashboard ← طيران 30s ← رجّع | لا تحوّل لـLogin ولا دوّامة؛ يعود ويتزامن | لوغ: `ConnectivityStore` → `syncNow(force: true)` |
| **S8** | خروج ثم دخول | A: خروج ← إدخال نفس الحساب | Dashboard + `Disponible` كما كان | جلسة جديدة · `is_logged_in = true` |
| **S9** | جلسة منتهية | B (Dashboard): Auth ← احذف جلسة المستخدم. A: افتح | **شاشة الدخول** (لا دوّامة، لا `pending`) | R6: `checkInitialSession` يعيد `null` |
| **S10** | تبديل حساب | A: خروج ← دخول محترف **آخر** (`pro.b@…`) بلا موافقة | شاشة انتظار **B** — ولا أثر لحالة A | سجل A لا يُستنسخ · لا سجل مكرّر |

## 2. فحوص القاعدة (بعد كل سيناريو)

```sql
-- حالة المحترف
select id, status, is_verified, rejection_reason, approved_at
  from public.professionals
 where id = '<auth_uid>';

-- لا سجلات مكرّرة: يجب أن يعيد 0
select auth_uid, count(*)
  from public.professionals
 group by auth_uid
having count(*) > 1;
```

## 3. معايير القبول

يُعتبر البروتوكول **ناجحًا** فقط إذا:

1. كل السيناريوهات ✅ (بلا استثناء).
2. **لا مرة واحدة** ظهر خيار «في انتظار التحقق» لحساب `approved`.
3. **لا دوّامة بلا مخرج** في أي سيناريو (كل شاشة فيها زر خروج/إعادة محاولة).
4. الموافقة تصل **بلا** إعادة تشغيل ولا تسجيل خروج (S2).
5. بطاقة **واحدة** لكل محترف في لوحة الأدمن.
